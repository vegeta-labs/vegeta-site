The problem

  1. 01

    One or two shared inboxes

    Payment questions, payment confirmations, KYC files, withdrawals and changes of details all land in the same place.

  2. 02

    Every email needs a lookup

    Someone works out what it is, finds the investor and the deal, checks the ledger and replies.

  3. 03

    The risky ones look ordinary

    A criminal claims the bank details have changed, often after intercepting emails or taking over a mailbox. UK Finance counted £41.3m lost to these invoice and mandate scams in 2025, 68% of it from business accounts.

  4. 04

    Generic tools don’t know deals

    A payment confirmation is not proof of receipt, and a passport scan by email is not a KYC check.

Fraud figures: UK Finance, Annual Fraud Report 2026 (figures for 2025), invoice and mandate scams.

Categories, templates, queues and deadlines are configuration, not code.

It reads. It suggests. It never sends.

No code path sends email or writes to a mailbox, and a CI check fails the build on any mail-write call. A person sends every reply.

Changed bank details
Bank details in an email are never applied to any record. Fixed reply, a call-back to the number on file, a cooling-off period, a second person.
Look-alike senders
Look-alike domains, mismatched display names and a different Reply-To raise the risk. Record data goes only to an authenticated sender entitled to see it.
Instructions hidden in an email
The model has no tools, writes no outbound text and chooses no template, and it can never lower the risk.
Personal data and model providers
Recognised personal values are redacted before any model sees the text, local or hosted, and possible ID documents never reach a model. A hosted provider refuses to start until you record a data processing agreement, unless you override it, which shows a warning.
Malicious attachments
Every attachment is virus-scanned, then parsed in a separate sandboxed container with no network.
Stored data and the audit trail
All text in the database is encrypted; only ids, types, hashes, times, amounts and the last four characters of each deal’s receiving accounts are kept in the clear. The audit log is hash-chained, the app’s own database roles cannot change or delete it, and a daily export of its latest hash, kept off the server, shows if recent records go missing.

FAQ

What it is

What does it not do?

It does not send email, write drafts or change anything in your mailbox. It does not move money, connect to a bank or change business records, including Goten’s. It does not verify KYC. It does not read images or scans: there is no OCR.

What does it cost?

The software is free and open source under the Apache-2.0 licence. You pay for your own server and, if you use one, a hosted model. The demo and the tests in CI run on recorded model replies, with no model calls.

Setting it up

How do I install it?

With Docker Compose on your own server: separate containers for the app, maintenance, the database, the virus scanner and a sandboxed attachment parser. The quick start walks through it, and the demo runs on your own machine with fictional data and no outbound connections.

Which mailboxes can it read?

IMAP (opened read-only), .eml import, Gmail (read-only, one consent per mailbox) and Microsoft 365 (read permission on the mailboxes you name, checked at every start). Microsoft 365 and Gmail push notifications (Pub/Sub) were tested only against simulated services. Gmail polling was tested on one personal Gmail account.

Which model does it use? Can I use a local one?

Anthropic Claude, or a local model through Ollama. A local model gets the same redacted text. By default a hosted provider refuses to start until you record that a data processing agreement exists; an explicit override starts it with a warning in the log and in the review screens.

Can I change the categories and replies?

Yes. Categories, queues, reply templates and deadlines are configuration files. The investment categories in the list above are only the default.

Who can do what?

Three roles: reviewer, approver and admin. Sign in with local accounts or with your own identity provider (OIDC). Admins manage users and import directories through the API, as described in Users and directory.

Your data

Where does my data live?

On your own server. The software has no analytics. Your data goes only where you configure: your mailboxes, your model provider and, if you use them, your sign-in provider, a webhook and your KYC folder or webhook. The virus scanner also downloads virus database updates.

What is sent to the model?

Only redacted text: the subject, display names, the body, attachment file names and the text of attachments that are not possible KYC documents. Values that match the documented patterns are replaced with placeholders first: IBANs, UK account numbers and sort codes, UK ID numbers, dates of birth, UK addresses, phone numbers, the local part of email addresses and the names in your directory. Other values, such as a name that is not in your directory, are not recognised (what is redacted). Account and ID placeholders are never turned back into values, even on screen. Amounts, references and UETRs are kept, because sorting needs them.

What happens to passports and other ID documents?

Code decides whether an attachment may be a KYC document: by its file name, by its text (such as a passport machine-readable line), or because it is an image, a scan or cannot be checked. A narrow, configurable exception keeps small inline signature images only when strict structural checks pass; images are never read or sent to any model. A reduced ID image or data in permitted image metadata can meet that exception and stay in the archive. Other possible KYC content is never sent to any model, local or hosted; it is transferred to your own KYC folder or webhook and then removed from the app. The release notes and data-protection templates explain this tradeoff.

What does it store, and for how long?

The original email, its attachments and the Case; possible KYC documents are transferred to you and then removed. All text in the database is encrypted, except the last four characters of each deal’s receiving accounts. Emails and old directory versions are deleted after the retention period you set, by a daily job; audit rows, which hold no personal data, are kept. Your backups keep data for as long as your backup policy keeps them.

Risk and trust

How does it spot impersonation?

A display name that doesn’t match the address, a look-alike domain, a different Reply-To and a first-time sender who gives an account number all raise the risk. A reply that discloses someone’s records goes only to an authenticated sender who is entitled to see them.

How do you know it works?

The rules are compared with an independent Python implementation, and mutation checks test the tests. Fictional test emails were written by independent agents that saw only the requirements: a development set, run in CI on recorded model replies, and a separate held-out set that development never read, newly written for v0.3.0 and run once with a real model. The results are on this page and in the release notes.

Is it ready for real mailboxes?

It is version 0.4.0: only what is built and tested is described here, and the release notes list its limits; for example, it has not been tested with real production mail volumes. Read the security model and fill in the DPIA and LIA templates before connecting a real mailbox. Report problems through the feedback form, without real investor details.
